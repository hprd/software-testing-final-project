# Proposed subject-selection protocol

Status: protocol drafted before the evaluation; it has not yet been applied. The existing Commons Lang and Commons IO candidates are exploratory, not held-out results.

1. Recover the original NonDex evaluation subject list and exact revisions from the paper's artifacts or a cited replication dataset; retain the source and record any unavailable revisions. Do not infer a complete list from the few projects named in the tool paper. Freeze the list and revisions before inspecting candidate outcomes.
2. For each subject, record repository URL, revision, build system, required JDK, checkout/build/test outcomes, and exclusion reason. Include unsuccessful and zero-use subjects in the ledger. Run baseline and stock NonDex under recorded configurations wherever feasible.
3. Inventory candidate API usage in production and test code, including dependencies where feasible. Record the method, overload, location, how calls were resolved, and limitations. Treat keyword counts as leads, not resolved usage or counts of affected tests. Record unsupported API families with version-specific documentation and check the pinned NonDex implementation.
4. If the fixed subjects have insufficient relevant calls or runnable tests, pre-register an additional source, snapshot date, objective ranking or sampling method, sample size, eligibility criteria, and stopping rule before examining outcomes. Preserve the complete selection ledger and report any later changes. Do not claim an objective supplemental cohort until these choices are fixed and applied.
5. Use the already inspected projects for exploration. Where practical, reserve a separately selected set for evaluation; record any overlap or contamination. Avoid selecting projects based on observed failures.
6. For each test, record baseline and stock-NonDex runs, perturbation and seed, documented allowed variation and constraints, validation controls, outcome, and investigation. Categorize as candidate, confirmed failure under a validated perturbation, rejected, or inconclusive. Report denominators, exclusions, invalid perturbations, and unresolved cases as well as findings.
7. Evaluate reconstruction of supported APIs separately from genuinely new coverage. Report discovery and generation quality, manual corrections, cost and runtime, and confirmed failures where the necessary ground truth exists. A compile or passing control provides evidence, not proof of contract compliance.
