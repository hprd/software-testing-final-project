# Supported APIs

This page describes the **active public NonDex implementation at revision [`f1f407ce3e026f597567e7d96ee08cb08875690f`](https://github.com/TestingResearchIllinois/NonDex/tree/f1f407ce3e026f597567e7d96ee08cb08875690f)** (`2.2.5-SNAPSHOT`). Audited November 20, 2026. Coverage depends on the JDK implementation and the execution path; naming a collection class does not imply that all of its methods are perturbed.

The audit covers the complete instrumentation registry, every standard method selector, and all seven special transformers. It also tests the public entry points and bypass paths described below. It does not enumerate every application method that could transitively call an instrumented API, or certify every perturbation as contract preserving.

## Directly instrumented public methods

These methods have NonDex calls injected into their bytecode. Except for the caveats below, the array-returning methods shuffle the returned array. Method names below include only the signatures listed, not every method on the class.

| Class | Methods | Effect / qualification |
| --- | --- | --- |
| `java.lang.Class` | `getClasses()`, `getDeclaredClasses()`, `getFields()`, `getDeclaredFields()`, `getMethods()`, `getDeclaredMethods()`, `getConstructors()`, `getDeclaredConstructors()`, `getAnnotations()`, `getDeclaredAnnotations()` | Shuffles each returned array. |
| `java.lang.reflect.Method` | `getExceptionTypes()`, `getGenericExceptionTypes()`, `getDeclaredAnnotations()` | Shuffles each returned array. |
| `java.lang.reflect.Method` | `getParameterAnnotations()` | Shuffles annotations **within each parameter's array**; does not shuffle the parameter positions. |
| `java.lang.reflect.Field` | `getDeclaredAnnotations()` | Shuffles the returned array. |
| `java.lang.reflect.Field` | `getAnnotationsByType(Class<T>)` | **Active, but has a contract correctness issue for repeatable annotations.** See below; do not treat failures on this path as established client bugs. |
| `java.io.File` | `list()`, `list(FilenameFilter)`, `listFiles()`, `listFiles(FilenameFilter)`, `listFiles(FileFilter)` | Shuffles each returned array. Null results are left unchanged. |
| `java.io.File` | `listRoots()` | Hook verified in generated bytecode. This audit's Linux systems expose one root, so runtime shuffling is a no-op; no multi-root behavior was exercised. |
| `java.text.BreakIterator` | `getAvailableLocales()` | Shuffles the returned array. |
| `java.text.Collator` | `getAvailableLocales()` | Shuffles the returned array. |
| `java.text.DateFormat` | `getAvailableLocales()` | Shuffles the returned array. |
| `java.text.DateFormatSymbols` | `getZoneStrings()` | Randomly retains the existing rows or extends **each inner row by one null slot**. Does not shuffle the zones or the defined columns. |
| `java.util.PriorityQueue` | `toArray()`, `toArray(T[])` | Shuffles the returned array. |
| `java.util.concurrent.PriorityBlockingQueue` | `toArray()`, `toArray(T[])`, `toString()` | Shuffles arrays; replaces `toString()` with a representation based on a shuffled snapshot. |

The standard selector uses the class and method name, so all existing overloads of `File.list`, `File.listFiles`, and `PriorityQueue.toArray` match. `Method` and `PriorityBlockingQueue` use dedicated transformers. Array shuffling returns immediately for null arrays or arrays with fewer than two elements; a hook does not guarantee a changed result on every call.

Source: [standard method selectors](https://github.com/TestingResearchIllinois/NonDex/blob/f1f407ce3e026f597567e7d96ee08cb08875690f/nondex-instrumentation/src/main/java/edu/illinois/nondex/instr/ClassVisitorShufflingAdder.java), [Method transformer](https://github.com/TestingResearchIllinois/NonDex/blob/f1f407ce3e026f597567e7d96ee08cb08875690f/nondex-instrumentation/src/main/java/edu/illinois/nondex/instr/MethodShufflingAdder.java), [PriorityBlockingQueue transformer](https://github.com/TestingResearchIllinois/NonDex/blob/f1f407ce3e026f597567e7d96ee08cb08875690f/nondex-instrumentation/src/main/java/edu/illinois/nondex/instr/PriorityBlockingQueueShufflingAdder.java), and [runtime control](https://github.com/TestingResearchIllinois/NonDex/blob/f1f407ce3e026f597567e7d96ee08cb08875690f/nondex-common/src/main/java/edu/illinois/nondex/shuffling/ControlNondeterminism.java).

## Collection traversal and indirect API coverage

NonDex also modifies internal iterator/traversal implementations. `entrySet()`, `keySet()`, and `values()` return views; randomization occurs when a supported path consumes a view, rather than in the view getter itself.

| Public class | Internal class instrumented | Public paths verified on both audited JDKs |
| --- | --- | --- |
| `java.util.HashMap` | `HashMap$HashIterator`, with an injected shuffler helper | All three views: `iterator()`, `toArray()`, `toArray(T[])`, `toString()`; map `toString()`. |
| `java.util.WeakHashMap` | `WeakHashMap$HashIterator` | All three views: `iterator()`, `toArray()`, `toArray(T[])`, `forEach(Consumer)`, `toString()`; map `toString()`. |
| `java.util.IdentityHashMap` | `IdentityHashMap$IdentityHashMapIterator` | All three views: `iterator()`, `forEach(Consumer)`, `toString()`; map `toString()`. **View array conversions bypass the hook.** |
| `java.util.concurrent.ConcurrentHashMap` | `ConcurrentHashMap$Traverser` | All three views: `iterator()`, `toArray()`, `toArray(T[])`, `forEach(Consumer)`, unsplit `spliterator().forEachRemaining(...)`, sequential `stream().toArray()`, `toString()`; map `toString()`, `forEach(BiConsumer)`, `keys()`, `elements()`. **Split/parallel traversal has a correctness problem; see below.** |
| `java.util.HashSet` | Backing `HashMap$HashIterator` | `iterator()`, `toArray()`, `toArray(T[])`, `forEach(Consumer)`, `toString()`. |
| `java.util.PriorityQueue` | `PriorityQueue$Itr`, plus its directly instrumented array methods | `iterator()`, `toArray()`, `toArray(T[])`, `toString()`. `forEach(Consumer)` was perturbed on Java 8 but bypassed the hook on Java 11. |
| `java.util.concurrent.PriorityBlockingQueue` | Its directly instrumented array methods / `toString()` | `iterator()`, `toArray()`, `toArray(T[])`, `toString()`, `spliterator().forEachRemaining(...)`, sequential and parallel `stream().toArray()` / `parallelStream().toArray()`. `forEach(Consumer)` was perturbed on Java 8 but bypassed the hook on Java 11. |
| `java.util.concurrent.DelayQueue` | Backing `PriorityQueue` array paths | `iterator()`, `toArray()`, `toArray(T[])`, `forEach(Consumer)`, `toString()`, `spliterator().forEachRemaining(...)`, sequential and parallel `stream().toArray()` / `parallelStream().toArray()`. |

These are concrete observations for unchanged, small collections on the two runtimes below. They do not establish correctness for concurrent modifications, resizing during traversal, every collision pattern, iterator removal, every inherited/default method, or every future JDK. The existing upstream tests separately exercise some iterator controls.

Further indirect coverage verified on both JDKs:

| Class | Methods | Mechanism |
| --- | --- | --- |
| `java.lang.reflect.Method` | `getAnnotations()` | Delegates to the instrumented declared-annotations path. |
| `java.lang.reflect.Field` | `getAnnotations()` | Delegates to the instrumented declared-annotations path. |
| `java.lang.reflect.Field` | `getDeclaredAnnotationsByType(Class<T>)` | Reaches the instrumented by-type path; shares the repeatable-annotation correctness concern below. |
| `java.text.DateFormatSymbols` | `getAvailableLocales()` | JDK locale-provider code reaches instrumented collection traversal/array conversion. This method is not a direct selector. |
| `java.text.DecimalFormatSymbols` | `getAvailableLocales()` | JDK locale-provider code reaches instrumented collection traversal/array conversion. This class is not in the instrumentation registry. |

Indirect coverage is implementation dependent. Other wrappers or subclasses can also reach these hooks, but cannot be assumed covered just because they wrap a listed class.

## Important bypasses

The following paths reached **zero NonDex exploration opportunities** in all three seeds on both audited JDKs, after warm-up:

| Class / path | Bypass observed |
| --- | --- |
| `HashMap` | Map `forEach(BiConsumer)`; all three views' `forEach(Consumer)`, spliterators, sequential streams, parallel streams. |
| `WeakHashMap` | Map `forEach(BiConsumer)`; all three views' spliterators, sequential streams, parallel streams. |
| `IdentityHashMap` | Map `forEach(BiConsumer)`; all three views' `toArray()` / `toArray(T[])`, spliterators, sequential streams, parallel streams. |
| `HashSet` | Spliterator, sequential stream, parallel stream. |
| `PriorityQueue` | Spliterator, sequential stream, parallel stream. |
| `Method` | `getAnnotationsByType(Class<T>)`, `getDeclaredAnnotationsByType(Class<T>)` for the repeated-annotation fixture. |

`PriorityQueue.forEach(Consumer)` and `PriorityBlockingQueue.forEach(Consumer)` additionally bypass the hooks on the audited Java 11 runtime, while reaching them on Java 8. Do not extrapolate these results to all Java 8–21 implementations.

## Instrumented paths with correctness problems

### ConcurrentHashMap split traversal

In the audit's unchanged six-entry map, `entrySet().parallelStream().toArray()`, `keySet().parallelStream().toArray()`, and `values().parallelStream().toArray()` produced incorrect element multisets under NonDex on **both Java 8 and Java 11**. Plain runs preserved the elements. The evidence matrix records per-seed violation counts and example expected/actual values.

The active transformer copies and shuffles the backing node array in every `ConcurrentHashMap$Traverser` constructor. Independent shuffled copies combined with split index ranges are a plausible cause of missing/duplicate elements; the audit demonstrates the symptom, not a repaired implementation. Unsplit traversal passing this fixture does not establish correctness for split traversal, parallel streams, or parallel bulk methods. These paths must not be advertised as validated contract-preserving support.

### Repeated field annotations

`Field.getAnnotationsByType(Class<T>)` is actively shuffled, and the audit observed multiple orders for `@Tag(1) @Tag(2) @Tag(3)`. Its indirect `getDeclaredAnnotationsByType` path is likewise affected. However, repeated annotations have a specified order based on the container's `value` array. Membership preservation alone is insufficient here. The implementation is active, but that arbitrary permutation is not valid for this fixture. See the [AnnotatedElement ordering contract](https://docs.oracle.com/en/java/javase/22/docs/api/java.base/java/lang/reflect/AnnotatedElement.html) and [Java 8 JLS, repeated annotations](https://docs.oracle.com/javase/specs/jls/se8/html/jls-9.html#jls-9.7.5).

## Object.hashCode(): original prototype versus public tool

`Object.hashCode()` and `System.identityHashCode(Object)` are **not perturbed by this public implementation**. Neither has an active transformer or JVM hash-code option in this checkout. The audit's stable-object controls reached no exploration opportunities; the source registry independently confirms the omission.

The [original 2016 paper, Section III-C](https://mir.cs.illinois.edu/marinov/publications/ShiETAL16NonDex.pdf) describes changing OpenJDK's native C++ implementation of `hashCode()`. That was a custom-JVM research prototype. [Alex Gyori's 2017 dissertation, printed page 28, footnote 1](https://mir.cs.illinois.edu/marinov/publications/Gyori17PhD.pdf#page=40) explicitly explains that the public tool omits native hash-code handling because it exposed no bugs in their experiments and would complicate implementation and portability. Ordinary JVM hash-code variability is not NonDex-controlled support.

`Hashtable.keys()` and `java.nio.file.Files.list(Path)` likewise have no active selectors here and reached no choices in the controls. The separate parent-project Hashtable experiment does not extend stock NonDex.

## How coverage was verified

The [reproducible verifier](verification/README.md) builds **`nondex-common` and `nondex-instrumentation` from the pinned source**, generates fresh instrumented classes, and checks all 15 registered class entries and all 20 unique standard class/method selectors against the generated bytecode. Dedicated transformers cover the remaining methods and internal traversal classes.

Do not infer active coverage from `nondex-core/src/main/java` alone: that module contains historical modified JDK sources, and its POM disables the default compilation execution. Likewise, the presence of a test class is not evidence that an API is selected or perturbed.

Runtime verification used:

- Red Hat OpenJDK **8u514**, build `25.514-b01`.
- Eclipse Temurin **11.0.33+10**.
- NonDex `FULL` mode; seeds **933178, 974622, 1016066**.
- **175 public API/path probes per JVM**, each repeated 24 times after warm-up, in plain and freshly instrumented runs: **2,100 probe measurements** across both JDKs and all runs.
- Per-call NonDex opportunity counters, distinct result counts, and element-multiset checks for array/traversal probes. Zone-string probes also checked the original seven columns and optional trailing null.
- All **92 existing upstream JUnit tests passed on each JDK**. Those tests do not cover all the bypasses or correctness issues above.

See the complete [175-row coverage matrix](verification/COVERAGE-MATRIX.md), [Java 8 manifest/results](verification/java8-results.json), and [Java 11 manifest/results](verification/java11-results.json). The manifests include source/dependency hashes and injected method signatures. **Java 17 and 21, other vendors, and multi-root file systems were not runtime-tested in this audit.** A passing small-fixture probe demonstrates active coverage and its checked invariants, not general contract correctness.
