# API variation workflow: task boundaries and gates

This document describes the current research workflow and its known boundaries. A task's output is evidence for the next task, not an automatic proof of correctness. The coordinator currently invokes the existing staged reviewer and the opt-in registered Hashtable fixture; the evidence-first scenario reviewer described below remains a separate evaluation prototype. An opt-in two-pass normative review can run before the existing staged variation review; neither output is automatically verified.

1. **Subject baseline and inventory** (`run.py`). Record the project revision, tracked changes, toolchain, command and baseline outcome. Inventory calls with javac. Output call sites and diagnostics. A failure to execute a test, unresolved owner/signature, incomplete source scope, or approximate classpath is an explicit limitation. A failed baseline must not be attributed to perturbation.
2. **Documentation collection** (`contracts_deep_dive.py`). Group compiler-observed calls and collect JDK source comments, retaining the JDK source archive digest. Collected documentation is not yet a contract conclusion. Third-party and unavailable sources remain unresolved.
3. **Contract source resolution** (`resolve_contracts.py`). Match a source declaration only if name and parameter types match textually and uniquely. Attach identified class documentation and limited related source passages with stable IDs. The match is not proof of runtime dispatch, generic erasure, linked/inherited contract closure or receiver behavior. When uncertain, leave a gap rather than guess.
4. **Evidence selection** (`review_cases_isolated.py`, experimental). Given one API and behavior dimension, ask for a bounded set of exact source passages. Check source ID, passage integrity, and quotation. Record missing evidence. Selection is provisional, and missing a source can hide constraints.
5. **Scenario assessment** (experimental). For a concrete input and proposed alternative, ask for a provisional candidate/invalid/inconclusive assessment using the selected excerpts. In a separate request, assess the scenario against original passages without the first verdict. Do not treat model agreement as verification: both calls use the same model. Disagreement or no selected evidence is inconclusive. The control suite supplies scenarios; it does not evaluate discovery of new alternatives.
6. **Human contract and site review**. Check conditions, all applicable guarantees and the concrete receiver. Trace returned values into assertions and other uses. Keep model proposals, manually reviewed contract interpretations and potential site dependencies separate. The existing `site-cases.json` covers one manually reviewed narrow case; automated cross-statement and interprocedural tracing are not implemented.
7. **Implementation and controls** (`experiment.py`). An explicitly selected registered adapter is independent of model prose. Verify subject/fixture/toolchain fingerprints, run an unperturbed baseline, build the fixture, and check its controls. The only registered implementation is a plain two-key Hashtable experiment. Unknown APIs and arbitrary model-supplied code are not executable by this flow.
8. **Attribution**. Require the same target test, an unchanged scoped subject, a fresh Surefire XML report for that test, matching failure and source location, passing controls, and a fresh passing unperturbed recheck after the patched run. A single recheck cannot rule out all flakiness. A failing build, unrelated test failure, stale/missing report, absent test, baseline failure or failed controls is inconclusive. `confirmed_scoped_order_dependency` is only the already reviewed Hashtable witness; it does not certify a general implementation. Passing tests do not prove the absence of a dependency.

## Evaluation and iteration

`evaluation/cases.json` holds nine manually reviewed development controls across five APIs. `evaluation/score.py` reports the full confusion matrix and missing cases. `evaluation/merge_results.py` combines nonoverlapping interrupted runs without hiding incomplete status. Do not use the development set as a held-out accuracy estimate. For a reliability claim, independently review a held-out set with positive, negative and inconclusive examples; define thresholds before running it, report false positives and missing/errored cases, and include contract-preserving implementation checks and call-site attribution. No such general reliability claim has yet been established.

Run the narrow checks with `python3.11 Agent/tests/test_resolution.py`, `test_review_cases_isolated.py`, `test_experiment.py`, `test_pipeline.py`, and `test_merge_results.py` (each under `Agent/tests/`). See `README.md` for full commands and `live-evaluation.md` for actual model outputs and experiment evidence.

The experimental `--constraint-check` option adds a fourth, isolated model request asking separately about explicit contradictions and undefined-result conditions. Its result can only downgrade a proposed classification to inconclusive; it cannot upgrade or approve a candidate. It still uses the same model and can miss a constraint. It remains outside the coordinator and requires manual review.

The experimental scenario reviewer writes a sidecar checkpoint after each completed model role, including source/run hashes and the raw response. A checkpoint is labeled `in_progress_or_interrupted`; it is not a completed classification and does not automatically resume. Existing output or checkpoints are preserved, so use a new output path for another run. Results from a process started before this change do not contain these checkpoints or the newer metadata.

For newly prepared documentation, `coverage.json` records the generated `jdk-docs.jsonl` hash. The resolver verifies it and uses the documentation artifact, rather than queue-embedded comment text, as its passage source. Older artifacts without that hash are marked `unverified`; a mismatch is rejected. A hash stored alongside an artifact is an integrity check, not independent authentication of the JDK source or full contract applicability.

## Two-pass normative task

`normative_review.py` first extracts source-attributed normative statements from each selected source chunk. Once all extractions finish, a separate pass audits each statement's wording, conditions, scope and proposed kind, and checks for omissions in that chunk. Each pass is a call to the same model. Missing linked or inherited sources, boundaries between chunks, extraction errors and output caps prevent a completeness guarantee. `requires_human_review` means the responses passed structural checks, not that all statements are correct or complete. The coordinator's optional normative gate blocks later staged review on incomplete responses, audit omissions, unsupported or unclear statement/kind judgments, or a model warning that more statements may exist, but does not treat the audit as ground truth or feed its claims into the staged review.
